# CXPAY 渐进式架构优化设计

## 1. 背景

CXPAY 已形成支付网关、商户与管理后台、个人码账单采集、支付插件、云监控服务和桌面采集端等完整业务能力。当前架构采用模块化单体支付核心，并通过插件和独立采集服务扩展支付能力，整体方向可继续演进。

现阶段的主要矛盾不是功能不足，而是功能增长速度超过了数据库迁移、资金账本、可靠消息、权限边界和模块拆分能力。部分核心类同时承担多个业务职责，且当前工作区包含尚未提交的云授权与插件市场修改，优化过程中必须保护这些现有改动。

## 2. 目标

本次优化采用“风险优先、随改随拆”的渐进方式，目标如下：

1. 消除云授权、订单号、手续费冲正、通知可靠性、权限和插件 TLS 校验等生产阻断风险。
2. 建立可重复、可追踪的数据库迁移机制，使全新安装和版本升级使用同一套结构演进流程。
3. 将承担多个业务职责的大类拆成边界清晰、可独立测试的应用服务和控制器。
4. 保持已有 URL、请求参数、签名算法和响应结构兼容，避免无必要的业务中断。
5. 为真实 MySQL、Redis、多 Worker 并发和故障恢复建立自动化验证能力。

## 3. 非目标

本阶段不执行以下工作：

- 不将支付核心全面拆成微服务。
- 不替换 Webman、Workerman、Eloquent 或现有支付 SDK。
- 不对管理端和商户端前端进行视觉重构。
- 不进行与安全、资金一致性、可靠性或大类拆分无关的功能扩展。
- 不一次性改写全部旧代码或强制统一所有历史命名。

## 4. 方案选择

### 4.1 采用方案：渐进式领域治理

每个生产风险形成一个独立、可测试、可回滚的交付单元；修改某一业务链路时，同步拆分该链路中的大类。该方案能在持续交付业务价值的同时降低重构回归风险。

### 4.2 未采用方案：一次性领域重写

一次性重写可以获得更整齐的最终结构，但需要同时迁移订单、商户、插件、账单和通知链路，资金系统的验证成本和回滚风险过高。

### 4.3 未采用方案：只拆文件不修业务缺陷

机械移动方法可以快速降低文件行数，但无法改善资金模型、事务边界和模块耦合，且容易把隐含缺陷分散到更多文件中。

## 5. 总体实施顺序

### 5.1 第一阶段：生产阻断项

1. 保护云授权和插件市场接口，停止返回完整许可证密钥，并在支付闭环完成前关闭插件购买发证。
2. 建立版本化数据库迁移，修复初始化结构与当前模型、服务不一致的问题。
3. 替换多进程不安全且可预测的订单号生成器。
4. 记录手续费现金和套餐优惠额度的预留来源，并在订单关闭时原路冲正。
5. 建立数据库事务 Outbox，保证订单结算后商户通知不会因 Redis 或进程故障丢失。
6. 使账单匹配能够区分首次结算、同源重复和异源冲突。
7. 将管理权限异常策略改为拒绝，并恢复插件远程授权请求的 TLS 验证。

### 5.2 第二阶段：大类拆分

- 拆分 `OrderService` 的订单创建、支付初始化、结算、关闭、手续费预留和通道路由职责。
- 拆分 `AdminController` 的认证、仪表盘、商户、通道、安全配置和系统升级职责。
- 拆分 `MerchantApiController` 的认证、资料、仪表盘、套餐、告警和通知职责。
- 将 `InstallController` 收敛为 HTTP 入口，把环境检测、迁移、配置写入和安装锁交给独立服务。
- 将 `CloudApplication` 收敛为协议路由入口，把认证会话、订单登记、账单事件、审核和状态查询交给独立处理器。
- 测试文件跟随业务用例拆分，避免形成新的超大测试类。

### 5.3 第三阶段：工程化治理

- 通过容器注入订单仓储、账本、支付网关、通知 Outbox 和风控接口。
- 统一金额、订单状态和财务流水的表达方式。
- 合并旧 `packvip` 与新套餐体系。
- 修正 Docker 持久化目录并将会话迁移到 Redis。
- 清理仓库中的依赖包、构建产物和大型压缩文件。
- 增加多进程并发和依赖故障注入测试。

## 6. 订单领域拆分

### 6.1 兼容门面

第一轮拆分保留 `OrderService` 的公共方法签名，使现有控制器、定时任务和测试无需一次性迁移。`OrderService` 只负责参数转交和结果兼容，不再承载具体业务规则。

### 6.2 新组件职责

| 组件 | 单一职责 |
|---|---|
| `CreateOrderService` | 校验订单请求、执行限频、预留手续费并持久化订单 |
| `PaymentInitializationService` | 领取支付初始化权、调用支付驱动并保存支付结果 |
| `OrderSettlementService` | 锁定订单和商户、校验支付来源、完成结算和写入 Outbox |
| `CloseOrderService` | 关闭待支付订单并按原资金来源冲正手续费 |
| `FeeReservationService` | 计算、预留、确认和释放现金及套餐优惠额度 |
| `ChannelRoutingService` | 根据商户、支付类型、金额、权重和备用关系选择通道 |
| `OrderNumberGenerator` | 生成不可预测、跨进程安全并受数据库唯一约束保护的订单号 |

组件之间只传递明确的请求对象、结果对象或领域枚举，不直接调用对方的私有实现。

## 7. 手续费预留与冲正

新订单需要记录以下数据：

- `fee_reserved_cash`：从商户现金余额预留的手续费。
- `fee_reserved_discount`：从套餐优惠额度预留的手续费。
- `fee_reservation_status`：`reserved`、`consumed` 或 `released`。

创建订单时，订单、商户余额、套餐额度和财务流水必须在同一事务内更新。支付成功时将预留状态改为已消费；订单关闭时分别退回现金账户和套餐账户，并写入冲正流水。

升级前已存在且无法确定资金来源的待支付订单继续使用原退款规则，同时写入审计告警。该兼容分支只服务存量订单；迁移完成后的新订单不允许缺少预留来源。

所有金额继续使用数据库定点小数，并在应用层通过统一金额规范化组件处理；后续阶段再评估是否迁移为整数分。

## 8. 结算结果与账单匹配

结算服务返回明确结果枚举：

- `NEWLY_PAID`：当前调用首次完成结算。
- `ALREADY_PAID_SAME_SOURCE`：相同账单或相同上游交易重复通知。
- `ALREADY_PAID_OTHER_SOURCE`：订单已由其他账单完成结算。
- `ORDER_NOT_FOUND`：没有找到可处理订单。
- `AMOUNT_CONFLICT`：账单金额与订单金额不一致。

只有 `NEWLY_PAID` 和可验证的 `ALREADY_PAID_SAME_SOURCE` 可以把账单标记为已匹配。订单与支付来源之间建立数据库唯一约束，异源重复事件进入人工审核，不得静默吞掉。

## 9. 商户通知 Outbox

订单结算事务按固定顺序执行：

1. 锁定商户记录。
2. 锁定订单记录。
3. 校验订单状态、金额和支付来源。
4. 更新订单、商户余额、统计和财务流水。
5. 插入 `merchant_notify_outbox`。
6. 提交事务。

后台分发器通过租约字段领取待发送记录，成功后记录响应摘要和完成时间，失败后记录重试次数、下次执行时间及最终死信状态。Redis只作为唤醒和吞吐优化，不作为通知可靠性的唯一依据。

## 10. 控制器与云服务拆分

### 10.1 管理后台

`AdminController` 拆为：

- `AdminAuthController`
- `AdminDashboardController`
- `AdminMerchantController`
- `AdminChannelController`
- `AdminSecurityController`
- `SystemUpdateController`

### 10.2 商户 API

`MerchantApiController` 拆为：

- `MerchantAuthController`
- `MerchantProfileController`
- `MerchantDashboardController`
- `MerchantPlanController`
- `MerchantAlertController`
- `MerchantNotifyController`

### 10.3 安装模块

`InstallController` 只解析请求和返回响应，具体工作拆给：

- `EnvironmentInspector`
- `DatabaseConnectionTester`
- `MigrationRunner`
- `EnvironmentFileWriter`
- `InstallationLock`
- `InstallApplicationService`

### 10.4 微信云监控服务

`CloudApplication::handle()` 保留为统一协议入口，内部委托给：

- `AuthSessionHandler`
- `CloudOrderHandler`
- `PaymentEventHandler`
- `ReviewEventHandler`
- `OperationsStatusHandler`

拆分后保持现有 URL、请求字段、认证协议和响应状态码不变。

## 11. 云授权与安全边界

- 站点信息接口不再返回完整许可证密钥，只返回脱敏标识和授权状态。
- 插件市场、购买和下载接口必须验证可识别的站点主体及请求签名。
- 插件购买在扣费订单、支付确认和幂等发证闭环完成前保持关闭。
- 管理员权限查询异常时，超级管理员以外的主体一律拒绝访问。
- 会话写操作增加显式 CSRF 防护；Bearer Token 接口继续使用令牌认证。
- 插件远程授权请求启用证书和主机名验证，并限制受信任授权域名。
- 内部异常记录到日志，对外只返回稳定错误码和不含敏感信息的中文提示。

## 12. 数据库迁移与安装

数据库结构以有序迁移文件为唯一来源，迁移执行器维护版本表并保证每个版本只执行一次。`install.sql` 不再独立演进，而是由基础结构与全部迁移生成或校验。

CI 中建立空数据库验证：

1. 执行全部迁移。
2. 创建管理员和商户。
3. 注册、登录并获取资料。
4. 创建订单并初始化支付。
5. 模拟支付成功和重复账单。
6. 验证手续费预留、冲正和财务流水。
7. 停止 Redis 后验证 Outbox 仍能恢复通知。

迁移必须支持项目声明的最低 MySQL 版本；不使用该版本不支持的 DDL 语法。

## 13. 兼容与发布策略

- HTTP 路由、字段、签名和响应结构默认保持不变。
- 数据库改动优先采用新增字段、表和索引，确认无旧版本读取后再删除历史结构。
- 大类拆分先通过兼容门面委托，新组件稳定后再迁移调用方。
- 插件启用、升级和回滚后执行 Workerman 平滑重启，避免不同 Worker 使用不同类版本。
- 每个生产风险单独提交，允许按任务回滚，不把所有重构压入一个提交。
- 当前工作区已有修改不自动纳入优化提交；实施前通过隔离工作区或明确的补丁迁移保护用户改动。

## 14. 测试策略

每个任务使用测试驱动流程：

1. 为现有接口补充特征测试，锁定兼容行为。
2. 为目标缺陷编写失败测试，并确认失败原因与缺陷一致。
3. 编写最小实现使测试通过。
4. 在测试保持通过的前提下拆分职责和清理重复。
5. 执行相关测试、完整 PHPUnit、PHP 语法检查和 Composer 配置校验。

测试层次包括：

- 单元测试：金额计算、订单号、状态枚举、权限策略和路由分发。
- 集成测试：真实 MySQL 事务、唯一约束、行锁和迁移。
- 故障测试：Redis不可用、通知进程崩溃、重复回调和插件授权服务不可用。
- 并发测试：多 Worker 同时创建订单、套餐购买和账单匹配。
- 接口契约测试：拆分控制器前后响应保持一致。

## 15. 完成标准

第一阶段完成时必须满足：

- 公共云授权接口无法获得完整许可证密钥或绕过扣费发证。
- 空数据库能够完成安装、注册、建单、支付结算和通知恢复。
- 多进程并发创建订单不产生重复订单号。
- 手续费现金和套餐优惠额度能够原路冲正。
- Redis或通知进程故障不会永久丢失商户通知。
- 两笔不同账单不能同时匹配同一订单。
- 权限和远程证书校验异常不会放行。

第二阶段完成时，核心生产类原则上控制在约 300 行以内。超过该规模的文件必须仍然只承担一个清晰业务职责，并在代码评审中说明保留理由。拆分不得改变现有接口契约。

## 16. 风险控制

- 资金模型修改先增加字段和双路径兼容，再迁移存量数据，不直接删除旧字段。
- Outbox 上线时保留原 Redis 消费兼容期，但禁止同一通知被两个调度器无幂等地发送。
- 云授权相关修改以当前工作区代码为基线进行人工核对，避免遗漏尚未提交的新增模型和迁移。
- 每一批只处理一个可独立验证的业务风险，完整回归通过后再进入下一批。
- 任何涉及生产数据的迁移都提供执行前检查、执行结果统计和可恢复方案。
