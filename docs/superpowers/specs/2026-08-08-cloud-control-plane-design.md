# CXPAY 独立云端控制面设计规格

> 状态：已完成会话设计确认，等待书面规格复核
>
> 日期：2026-08-08
>
> 目标版本：Cloud Control Plane 1.0

## 1. 背景

当前仓库同时包含 CXPAY 支付系统、授权中心原型、插件商城原型和多个支付监控云服务。微信监控数据面已经具备较完整的可靠性能力，但官方授权、源码下载、插件交易等服务端逻辑仍位于 CXPAY 主应用中，造成部署边界、数据库权限、密钥管理和发布周期耦合。

现有实现还存在以下上线阻断问题：

- 普通 CXPAY 部署携带官方云端服务端路由与模型；
- 公开站点信息接口可能返回完整授权密钥；
- 插件购买没有支付订单闭环，能够直接写入授权；
- 微信、QQ 和邮件登录供应商尚未接入；
- 云端运营、代理商和授权用户没有完整、隔离的后台；
- 插件下载仍依赖 `domain + auth_key`，无法识别具体安装实例；
- 源码包、更新包和插件包缺少统一的制品发布、签名和下载审计体系。

本设计将官方云端重构为与 CXPAY 支付系统完全独立部署的模块化控制面。

## 2. 目标与非目标

### 2.1 目标

1. 建立独立的 `services/cloud-control-plane` 服务、数据库、域名、密钥和发布流水线。
2. 为官方管理员、代理商和最终授权用户提供隔离的身份、租户和权限体系。
3. 完成源码授权、更新服务、支付插件购买、续费、退款和代理代开的交易闭环。
4. 使用指定 CXPAY 实例的商户 API 作为首个支付网关，并保持支付网关可替换。
5. 采用双分录账本管理代理商充值、扣款、退款和冲正。
6. 以规范化域名作为站点授权对象，以 Ed25519 公钥识别具体 CXPAY 安装实例。
7. 允许授权用户在云端工作台下载源码包和更新包。
8. 限制插件包只能由已激活的 CXPAY 插件商城下载和更新。
9. 建立不可变制品、平台签名、客户水印、短时下载凭证和完整下载审计。
10. 建立支付、履约、制品构建和通知的幂等及崩溃恢复机制。
11. 逐步迁移现有授权数据，不复制用户明文密码、实例私钥或 CXPAY 支付业务数据。

### 2.2 非目标

- 首期不拆成多个独立微服务或多个业务数据库；
- 首期不实现微信、支付宝官方支付直连，只实现 CXPAY 商户支付网关；
- 首期不让支付监控数据面直接访问控制面数据库；
- 首期不使用 Redis 保存余额、订单、授权等最终业务事实；
- 首期不允许用户从网页后台直接下载支付插件；
- 首期不建立长期双写迁移链路；
- 首期不把永久授权解释为永久免费获得所有未来重大版本。

## 3. 总体架构

采用独立模块化单体。控制面在一个应用和一个 MySQL 事务数据库中运行，内部按业务模块隔离，通过应用服务接口协作。

```text
CXPAY 支付系统
  ├─ 商户支付业务
  ├─ 本地插件商城客户端
  └─ 实例私钥与签名请求
            │ HTTPS
            ▼
Cloud Control Plane
  ├─ 官网与租户工作台
  ├─ 官方运营后台
  ├─ 身份、租户与代理关系
  ├─ 商品、订单、支付与账本
  ├─ 域名授权、插件授权与实例
  ├─ 制品、水印与下载
  └─ Outbox、审计与运维
            │ 独立协议
            ▼
支付监控数据面
  ├─ wx-monitor-cloud
  ├─ wxpay-clerk-service
  ├─ alipay-monitor-cloud
  └─ alipay-autoconfig-proxy
```

### 3.1 部署边界

控制面独立使用：

- `api.cloud.cxpay.com`：控制面 API；
- `cloud.cxpay.com`：授权用户和代理商工作台；
- `ops.cloud.cxpay.com`：官方运营后台；
- `www.cxpay.com`：官网、价格、文档和登录入口；
- 独立 MySQL 8 数据库；
- 独立 Redis 7，用于会话、限流和短期缓存；
- 私有 S3 兼容对象存储；
- 独立平台签名密钥、水印密钥、支付网关密钥和会话密钥；
- 独立 Web、Outbox、制品构建和对账 Worker；
- 独立日志、指标、备份、CI 和发布流程。

CXPAY 主系统只保留云端 API 客户端、实例私钥、本地插件商城、插件安装更新和授权状态查询。普通 CXPAY 进程不连接云端数据库，不持有云端管理密钥，也不运行云端授权服务端路由。

### 3.2 技术栈

- PHP 8.2；
- Webman 2；
- MySQL 8；
- Redis 7；
- S3 兼容对象存储；
- Libsodium Ed25519；
- Vue 3、TypeScript、Vite；
- PHPUnit；
- 数据库 Outbox 和独立 Worker。

## 4. 身份、租户与权限

### 4.1 租户类型

- `OFFICIAL`：官方运营组织；
- `AGENT`：代理商组织；
- `CUSTOMER`：最终授权客户组织。

用户与租户通过成员关系关联。用户可以属于多个租户，但每次会话和 API 请求必须明确当前租户。代理关系通过独立关系表表达，不依赖用户账号层级。

### 4.2 核心数据表

- `cloud_users`：邮箱、手机、密码摘要、状态、二次验证和最后登录信息；
- `cloud_tenants`：租户类型、名称、状态和创建信息；
- `cloud_tenant_members`：用户、租户、角色和成员状态；
- `cloud_tenant_relations`：代理商与下级客户关系；
- `cloud_agent_profiles`：代理等级、折扣策略、授信状态和限制。

### 4.3 权限原则

- 官方管理员拥有全局运营权限；
- 代理商只能管理被授权层级内的客户；
- 最终用户只能访问自己所属租户；
- 代理商不能读取客户密码、实例私钥、完整下载 Token 或水印密钥；
- 官方人员介入客户数据必须填写原因并形成审计事件；
- 不提供无痕模拟登录；
- 跨租户仓储调用必须显式接收 `TenantContext`；
- 业务表携带 `tenant_id`，数据库约束与集成测试共同校验隔离。

### 4.4 角色

官方角色：

- 超级管理员；
- 运营管理员；
- 财务人员；
- 制品发布人员；
- 客服人员；
- 只读审计员。

代理商角色：

- 所有者；
- 管理员；
- 财务；
- 业务操作员；
- 只读成员。

客户角色：

- 所有者；
- 管理员；
- 开发人员；
- 财务；
- 只读成员。

退款、人工调账、永久授权、制品发布、强制换绑和审计策略变更需要二次验证。人工调账和大额退款需要双人审批。

## 5. 账本、商品与订单

### 5.1 双分录账本

核心表：

- `cloud_ledger_accounts`：代理余额、平台资金和清算账户；
- `cloud_ledger_transactions`：充值、消费、退款和冲正业务交易；
- `cloud_ledger_postings`：不可变借贷分录；
- `cloud_wallet_snapshots`：事务内维护的查询余额和版本号。

不变量：

- 每笔交易借方合计等于贷方合计；
- 每笔交易带全局唯一幂等号；
- 已记账流水禁止修改或删除，只能追加冲正；
- 余额快照必须等于有效分录汇总；
- 余额不足时事务失败；
- 人工调账记录原因、操作人、审批人和关联审计事件。

### 5.2 商品

- `cloud_products`：源码授权、更新服务和支付插件；
- `cloud_product_prices`：月付、季付、年付、永久和代理等级价格；
- 商品价格在下单时写入订单项快照，后续调价不改变历史订单；
- 重大版本权益通过商品或版本策略表达，不从“永久”字面推导。

### 5.3 订单与支付

- `cloud_orders`：购买、续费、代理代开和充值订单；
- `cloud_order_items`：商品、域名、期限、原价、折扣和成交价快照；
- `cloud_payments`：CXPAY 商户订单和支付状态；
- `cloud_payment_inbox`：支付回调摘要、签名结果和处理状态；
- `cloud_refunds`：退款申请、网关退款和状态；
- `cloud_fulfillments`：订单履约幂等记录。

订单状态：

```text
PENDING → PAYING → PAID → FULFILLING → FULFILLED
                    └────→ REFUNDING → REFUNDED
PENDING/PAYING → CANCELLED/EXPIRED
```

用户支付通过 `PaymentGatewayInterface` 调用指定 CXPAY 实例的商户 API。回调必须先验签和持久化，再在事务内校验商户订单号、金额和币种。金额异常进入人工队列。定时对账任务主动查询长期 `PAYING` 订单，恢复丢失的异步通知。

支付成功只将订单标记为 `PAID` 并写入 Outbox；履约 Worker 通过唯一履约键创建或续期授权。重复回调和重复履约都必须返回幂等成功。

### 5.4 代理商充值与代开

充值订单支付成功后通过双分录增加代理余额。代理商代开使用 `WALLET` 订单，在同一个 MySQL 事务内锁定余额账户、扣款、写分录和发放授权。任一步失败全部回滚。

## 6. 域名授权、插件授权与实例

### 6.1 域名授权

- `cloud_site_licenses`：所属租户、规范化域名、源码产品、状态和到期时间；
- `cloud_entitlement_changes`：开通、续费、冻结、解冻、换绑和退款回收历史；
- `cloud_domain_change_requests`：换绑申请、冷却时间、审批和历史域名。

域名转为小写并完成 IDN 规范化。同一有效域名只能属于一个客户租户。更换域名保留原域名、原因、用户、IP、审批信息和时间。

### 6.2 插件授权

- `cloud_plugin_entitlements`：站点授权与插件商品的授权关系；
- 插件授权必须依附有效站点授权；
- 站点冻结后禁止插件下载和更新；
- 插件到期后禁止获取新版本；
- 已安装插件到期后的运行策略由商品规则明确配置；
- 云端网页后台只能购买、续费和查看插件，不能下载插件包。

### 6.3 CXPAY 实例

- `cloud_instances`：实例 UUID、站点授权、Ed25519 公钥、状态和最后活动时间；
- `cloud_instance_activations`：一次性激活码、用途和过期时间；
- `cloud_instance_key_history`：公钥轮换和吊销历史；
- `cloud_request_nonces`：实例 API 防重放随机数。

每个站点默认允许一个生产实例和一个短期迁移实例。迁移流程为“申请迁移 → 新实例激活 → 验证成功 → 旧实例吊销”。云端不生成、不接收也不保存 CXPAY 实例私钥。

实例请求规范串：

```text
HTTP_METHOD
REQUEST_PATH
TIMESTAMP
NONCE
BODY_SHA256
INSTANCE_ID
```

CXPAY 使用实例 Ed25519 私钥签名。云端校验 300 秒时间窗、持久化随机数、公钥状态、实例域名和授权状态。

## 7. 制品、水印与下载

### 7.1 制品

- `cloud_artifacts`：商品、版本、类型、对象键、SHA-256、大小、签名、兼容性和发布状态；
- `cloud_release_channels`：稳定、灰度和紧急修复渠道；
- 已发布制品不可覆盖，任何修改发布新版本；
- 源码包、更新包和插件包均使用 Ed25519 平台签名；
- 制品签名私钥仅供发布或构建 Worker 使用，不进入 Web 进程。

### 7.2 源码和更新包下载

授权用户登录云端工作台，选择自己名下的有效站点授权和可用版本。源码下载要求重新输入密码或完成二次验证。

流程：

```text
用户与租户鉴权
  → 域名与版本权益校验
  → 创建水印构建任务
  → 从不可变原始制品生成专属包
  → 写入用户、租户、域名、授权 ID 和下载 ID 水印
  → 计算哈希并签名
  → 上传私有对象存储
  → 创建一次性 5 分钟下载凭证
  → 下载并写入审计
```

- `cloud_watermark_jobs`：构建任务、租约、尝试次数和结果；
- `cloud_download_grants`：凭证哈希、制品、授权、主体、过期时间和使用状态；
- `cloud_download_logs`：版本、域名、用户、IP、User-Agent、结果和追踪 ID；
- 专属水印包默认保留 24 小时后清理；
- 私有对象存储不允许匿名读取；
- 下载凭证只保存哈希，不保存明文 Token。

### 7.3 插件下载和更新

插件只能由已激活的 CXPAY 插件商城调用实例 API 获取。云端依次校验：

1. 时间窗口和随机数；
2. 实例公钥未吊销；
3. 实例绑定域名；
4. 站点授权有效；
5. 插件授权有效；
6. CXPAY 和 PHP 版本兼容；
7. 制品签名、哈希和发布状态。

通过后返回一次性、5 分钟有效的下载凭证。CXPAY 下载后仍使用内置官方发布公钥验证插件签名。更新检查仅返回签名后的版本元数据，未授权实例只能获得商品购买信息。

## 9. API 与安全边界

API 分区：

```text
/api/public/v1/*       注册、登录和公开商品
/api/portal/v1/*       授权用户工作台
/api/agent/v1/*        代理商业务
/api/ops/v1/*          官方运营后台
/api/instance/v1/*     CXPAY 实例签名接口
/api/callback/v1/*     CXPAY 支付通知
```

每个区域使用独立中间件。`ops` 和 `portal` 使用不同会话、Cookie 域和前端入口。所有写接口支持 `Idempotency-Key`。错误响应统一包含稳定错误码、中文安全提示、请求追踪 ID 和可重试标志，不返回 SQL、堆栈、内部对象键或密钥。

旧 `domain + auth_key` 仅用于迁移期换取一次性实例激活码。任何查询接口都不得返回完整授权 Key。迁移结束后，插件下载和更新只接受实例签名。

## 10. 异步任务、审计与运维

### 10.1 异步任务

支付回调、授权履约、制品构建、下载包清理、通知和支付对账使用独立 Worker。任务使用数据库 Outbox、租约领取、指数退避和最大尝试次数。Worker 崩溃后，过期租约能够被其他 Worker 恢复。

### 10.2 审计

以下行为写入不可修改审计事件：

- 登录、二次验证和会话吊销；
- 用户、角色和租户关系变更；
- 代理调价、充值、扣款和冲正；
- 订单、支付、退款和异常处理；
- 授权开通、冻结、永久化和换绑；
- 实例激活、公钥轮换和吊销；
- 制品发布、灰度、下架和签名；
- 源码、更新包和插件下载；
- 管理员查看或导出敏感数据。

### 10.3 运维

- `/health` 只判断进程存活；
- `/ready` 校验 MySQL、Redis、对象存储和必要 Worker；
- 输出 Prometheus 指标和 JSON 结构化日志；
- 全链路使用请求追踪 ID；
- 监控支付异常、履约积压、构建失败、Outbox 失败和账本不平；
- MySQL 每日备份并定期恢复演练；
- 对象存储启用版本保护和生命周期策略；
- 使用版本化数据库迁移，禁止散落的手工 SQL 补丁；
- 密钥通过环境变量或 KMS 注入；
- 部署前运行迁移检查、后端测试、前端构建和 API 契约测试。

## 12. 迁移策略

采用受控切换，不建立长期双写：

1. CXPAY 增加运行角色保护，默认只运行支付系统；
2. 禁止现有公开接口返回完整授权 Key，禁止无支付直接授予插件授权；
3. 部署独立控制面、数据库、Redis、对象存储和 Worker；
4. 导入现有用户、代理商、域名授权、插件商品和插件授权；
5. 输出迁移数量、到期时间和域名唯一性校验报告；
6. 为已有用户发送一次性账号激活邀请；
7. 上传、校验并签名现有源码包、更新包和插件包；
8. 发布支持实例 Ed25519 激活的新 CXPAY；
9. 老站点用旧授权 Key 换取一次性实例激活码；
10. 迁移观察期结束后关闭旧插件下载协议；
11. 删除 CXPAY 本地云端服务端 Controller、模型和服务代码。

迁移不导入明文密码，不复制实例私钥，不允许控制面读取 CXPAY 支付业务数据库。

## 13. 实施里程碑

### M0：旧系统安全边界

- 关闭旧云端危险接口；
- 引入 CXPAY 支付运行角色；
- 保留本地云端客户端和插件商城入口；
- 为后续独立控制面定义 API 契约。

### M1：身份与租户

- 独立服务骨架和版本化迁移；
- 用户、租户、代理关系、角色和会话；
- 用户、代理和官方后台基础入口。

### M2：交易与账本

- 商品、价格、订单和支付网关；
- 代理充值和双分录账本；
- 支付 Inbox、Outbox、对账和履约。

### M3：授权与实例

- 域名和插件授权；
- 换绑、冻结、续费和退款回收；
- 实例激活、公钥、迁移和吊销；
- CXPAY 实例签名 API。

### M4：制品与下载

- 制品发布、兼容性、哈希和签名；
- 源码水印和更新包下载；
- 插件商城下载和更新；
- 短时凭证和下载审计。

### M5：后台、迁移与运维

- 用户、代理和官方运营完整后台；
- 迁移、校验和回滚工具；
- 指标、告警、备份和恢复演练；
- 全链路 CI 和端到端验收。

每个里程碑使用独立实现计划、测试周期和评审提交，不以一个超大改动一次完成。

## 14. 验收标准

1. 普通 CXPAY 部署不存在可调用的官方云端授权服务端接口。
2. 控制面与 CXPAY 使用不同数据库、密钥和部署配置。
3. 用户、代理和官方后台会话完全隔离。
4. 所有跨租户访问测试均被拒绝。
5. 未支付订单不产生授权。
6. 重复支付通知和重复履约只生效一次。
7. 代理余额扣款和授权发放原子一致。
8. 查询接口不返回完整授权 Key、实例私钥或签名私钥。
9. 源码和更新包只能由有权用户通过短期凭证下载。
10. 插件包只能由已激活且未吊销的 CXPAY 实例下载。
11. 插件包、更新元数据和客户专属包均能验证平台签名。
12. 高风险操作具有不可修改审计记录。
13. 支付、履约、构建和通知任务在进程崩溃后能够恢复。
14. CI 覆盖控制面后端、前端、迁移、契约和端到端测试。
15. 生产备份通过完整恢复演练。

## 15. 已确认决策

- 采用独立模块化单体，不继续在 CXPAY 主应用中扩展云端服务端；
- 同时建设官方运营后台、代理商后台和授权用户工作台；
- 支持代理商和下级客户；
- 代理商使用预充值余额和不可变双分录流水；
- 首个支付网关使用 CXPAY 商户 API；
- 源码授权绑定域名；
- 云端用户后台可以下载源码包和更新包；
- 支付插件只能在已安装 CXPAY 的插件商城下载和更新；
- 插件授权依附域名授权；
- CXPAY 实例使用域名与 Ed25519 公钥绑定。
